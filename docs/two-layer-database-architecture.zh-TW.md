# 兩層資料庫架構：編輯庫 → 正式庫

> 目的：讓客戶能自由編輯商品 / FAQ / 配送規則，但**永遠碰不到系統正式資料**，
> 避免客戶誤改欄位、刪資料、填錯格式，導致 n8n 與 LIFF 網站抓不到 / 抓錯資料。
>
> 本文件為「設計規格」，尚未實際建立 Notion 資料庫。建立時請完全依照本文件。

---

## 1. 為什麼要分兩層？

Notion 的權限**無法**做到「給客戶編輯內容、但鎖住欄位結構」。
只要給客戶編輯權，他就能：

- 刪掉或改名欄位（property）
- 改動下拉選項（select options）
- 刪整列資料
- 把數字欄位填成文字

以上任何一種都會讓 n8n 讀取失敗。因此採用**兩個分離的資料庫**：

```
┌──────────────────────┐    n8n 驗證 + 同步     ┌──────────────────────┐
│  ① 編輯庫 (Draft)     │  ──────────────────▶  │  ② 正式庫 (Live)      │
│  分享給客戶，可自由改   │   通過驗證才寫入        │  客戶無權限，系統專用   │
│                       │   失敗則擋下 + 通知你    │  n8n / LIFF 只「讀」   │
└──────────────────────┘                        └──────────────────────┘
        ▲                                                  │
        │ 客戶在這裡編輯                                      ▼
      客戶                                          LIFF 網站 / 自動化讀這裡
```

### 三個核心原則

1. **單向同步**：資料只從「編輯庫 → 正式庫」，絕不反向。
2. **正式庫唯讀**：除了 n8n 同步流程，沒有任何人能寫正式庫。
3. **驗證守門**：每一筆都先驗證，格式錯就擋下並通知，正式庫永遠保持乾淨。

---

## 2. 角色與權限

| 角色 | 編輯庫 (Draft) | 正式庫 (Live) |
|------|:---:|:---:|
| 客戶 | ✅ 可編輯 | ❌ 看不到 |
| 你（店家 / 管理者） | ✅ 可編輯 | 👁️ 唯讀（檢視用） |
| n8n 整合（API key） | ✅ 讀 + 寫狀態欄 | ✅ 寫入（唯一可寫者） |
| LIFF 網站 | ❌ 不讀 | 👁️ 唯讀 |

> Notion 設定要點：正式庫**不要**分享給客戶的 Notion 帳號 / email。
> 客戶只會拿到「編輯庫」的分享連結。

---

## 3. 穩定鍵（Stable Key）— 最重要的設計

兩個資料庫要靠一個**永不改變的編號**來配對，n8n 才知道「編輯庫這一列」對應「正式庫哪一列」。

- 每一類資料都有一個 `編號`（對應程式裡的 `id`）。
- **規則：客戶可以改任何欄位，但絕對不能改 `編號`。**
- 在編輯庫把 `編號` 欄位放在最右邊、加註說明「⚠️ 請勿修改」。
- 若客戶不慎改了編號，n8n 會視為「新的一筆」，驗證流程會以「找不到原編號」提示你人工確認。

### 不要用「刪除」，要用「停用」

客戶想下架商品時，**不要刪列**（刪了 n8n 難以追蹤）。
改為把 `上架狀態` 設為 `停用`。n8n 同步時，正式庫對應列也標記停用、LIFF 不顯示。

---

## 4. 同步狀態欄位（每個編輯庫都要有）

這些欄位由 **n8n 寫入**，讓客戶在編輯庫就能看到結果，不必碰正式庫：

| 欄位 | 型別 | 由誰寫 | 說明 |
|------|------|:---:|------|
| `同步狀態` | Select：`待同步` / `已同步` / `有錯誤` | n8n | 客戶存檔後預設待同步 |
| `錯誤訊息` | Text | n8n | 驗證失敗時填原因，例如「價格不是數字」 |
| `最後同步時間` | Date | n8n | 最近一次成功同步的時間 |

> 客戶看到 `有錯誤` + `錯誤訊息`，就能自己修正；正式庫完全不受影響。

---

## 5. 資料庫欄位規劃

以下三組，每組都有「① 編輯庫」與「② 正式庫」。
**正式庫欄位 = 編輯庫的資料欄位（不含同步狀態欄）**，型別必須與程式 `types.ts` 對齊。

### 5.1 商品 Products

對應 `Product`（`src/lib/types.ts`）。

#### ① 編輯庫：`商品編輯庫`

| 欄位（Notion） | 型別 | 客戶可改 | 對應 type | 驗證規則 |
|------|------|:---:|------|------|
| `商品名稱` | Title | ✅ | name | 必填、不可空白 |
| `編號` | Text | ⚠️ 勿改 | id | 必填、唯一、英數與 `-` |
| `分類` | Select | ✅ | category | 必須是：當季水果 / 進口水果 / 禮盒組合 / 學校團膳 / 公司訂購 |
| `說明` | Text | ✅ | description | 可空 |
| `規格` | Text | ✅ | spec | 必填 |
| `單位` | Text | ✅ | unit | 必填（箱 / 公斤 / 盒…） |
| `價格` | Number | ✅ | price | 必填、≥ 0 的數字 |
| `庫存狀態` | Select | ✅ | stockStatus | 必須是：有貨 / 少量 / 售完 / 預購 |
| `圖片網址` | URL | ✅ | imageUrl | 可空、需為 http(s) 開頭 |
| `排序` | Number | ✅ | sortOrder | 整數，預設 999 |
| `鮮度備註` | Text | ✅ | freshnessNote | 可空 |
| `上架狀態` | Select | ✅ | sourceStatus | 啟用 / 停用，預設啟用 |
| `同步狀態` | Select | ❌(n8n) | — | 見第 4 節 |
| `錯誤訊息` | Text | ❌(n8n) | — | 見第 4 節 |
| `最後同步時間` | Date | ❌(n8n) | — | 見第 4 節 |

#### ② 正式庫：`商品正式庫`

欄位同上「資料欄」部分（`商品名稱`、`編號`、`分類`、`說明`、`規格`、`單位`、`價格`、`庫存狀態`、`圖片網址`、`排序`、`鮮度備註`、`上架狀態`），
**不含**同步狀態三欄。另加：

| 欄位 | 型別 | 說明 |
|------|------|------|
| `來源更新時間` | Date | n8n 寫入，記錄此列最後同步自編輯庫的時間 |

> LIFF 網站 / n8n 一律讀 `商品正式庫`，且只讀 `上架狀態 = 啟用` 的列。

## 6. 驗證規則總表（n8n 同步前檢查）

| 類型 | 必過條件 | 失敗時 |
|------|------|------|
| 共同 | `編號` 必填且在該庫唯一 | 標記「有錯誤」+ 訊息「編號重複/缺漏」 |
| 共同 | 所有 Select 欄位的值必須在允許清單內 | 訊息「分類/狀態 不在允許清單」 |
| 商品 | `價格` 為 ≥ 0 數字；`商品名稱`/`規格`/`單位` 非空 | 訊息指出哪一欄 |
| 商品 | `圖片網址` 若有值需 http(s) 開頭 | 訊息「圖片網址格式錯」 |
| FAQ | `標題`/`內容` 非空 | 訊息指出哪一欄 |
| 配送 | 三個金額欄為 ≥ 0 數字；`涵蓋行政區` ≥ 1 項 | 訊息指出哪一欄 |

> 驗證失敗的列**不寫入正式庫**，並回寫 `同步狀態 = 有錯誤`、`錯誤訊息`，
> 同時可選擇推 LINE 通知你：「商品編輯庫第 N 筆有問題：xxx」。

## 7. n8n 同步流程（概念，先不實作）

1. **觸發**：定時（例如每 10 分鐘）或客戶在編輯庫按一個「送出審核」按鈕（之後可做）。
2. **讀取編輯庫**：抓 `同步狀態 != 已同步` 的列。
3. **逐列驗證**：套用第 6 節規則。
4. **分流**：
   - 通過 → 依 `編號` 在正式庫 upsert（有就更新、沒有就新增），寫 `來源更新時間`，回寫編輯庫 `同步狀態 = 已同步`、清空錯誤訊息、更新 `最後同步時間`。
   - 失敗 → 回寫編輯庫 `同步狀態 = 有錯誤` + `錯誤訊息`，**不動正式庫**。
5. **下架處理**：編輯庫 `上架狀態/狀態/啟用 = 停用/false` → 正式庫對應列同步為停用（不刪除）。
6. **（可選）通知**：有錯誤時推 LINE 給店家群組。

## 8. Notion 建立時的命名與設定建議

- 資料庫命名統一：`<類型>編輯庫` 與 `<類型>正式庫`，方便 n8n 對應。
- 兩庫的 Select 選項文字必須**完全一致**（含全形/半形），否則同步會比對失敗。
- 正式庫建立後，記下每個庫的 **Database ID** 與 **Data Source ID**，填到 n8n 與專案環境變數。
- 客戶分享：只分享「編輯庫」，權限給「可編輯」；正式庫不分享。
- 建議在編輯庫做兩個 View：
  - `待處理`（篩 `同步狀態 = 待同步 或 有錯誤`）給客戶看。
  - `全部` 給你看。

## 10. 建立後記下你自己的 ID

依本文件在 Notion 建立 6 個資料庫（3 類 × 編輯庫/正式庫）後：

- 記下每個資料庫的 **Database ID** 與 **Data Source ID**。
- 填入專案 `.env.local`（見 `.env.example` 的 `NOTION_*_DRAFT_DB_ID` / `NOTION_*_LIVE_DB_ID`）。
- 在 n8n 的 C1/C2/C3 同步 workflow 中指向同一組 ID。

## 11. n8n 同步 workflow（C1/C2/C3）

三條 workflow 共用同一套邏輯：每天固定時間自動觸發（亦可手動觸發）→ 讀編輯庫（`同步狀態 ≠ 已同步`）→ 驗證 → 通過則以 `編號` 為穩定鍵 upsert 正式庫 + 回寫「已同步」→ 不通過則回寫「有錯誤」，正式庫不動。

匯入範本見 `workflows/`，驗證規則見第 6 節。
